# M8.3 上下文区域估算与近期保留目标对照

2026-09-30。**结论：采纳消息区域估算修正，8k 近期保留目标未进入默认策略。** 12 次均通过外部判定；8k 相比修正后的 20k 累计 input 减少 11.6%，但 output 和耗时增加，且未压缩任务的采样波动明显。默认保留 20k，实际收益需更广的长任务样本确认。

## 缺陷与测量口径

`estimate_tokens` 的历史 usage 锚点估计的是整次历史请求和其后的消息。旧 `compaction._segment` 却对每条 assistant 单独调用它，把整次请求的 `usage.total_tokens` 当成该条消息大小；旧 `cost` 也把摘要区域之外的历史输入算入区域。这既可能产生过早切点，也可能降低工具结果占比、漏掉应当评估的成本压缩。

切点现按 `estimate_message_tokens`，成本区域按 `estimate_content_tokens` 累加消息自身内容；历史 usage 仅保留在压缩前诊断。下一请求的窗口和任务预算继续使用 `RequestSnapshot`。成本触发的近期保留目标单独命名为 `COST_KEEP_RECENT_TOKENS`，默认仍为 20,000；它是切点预算，整个请求还包含 system、工具 schema 和摘要，并非请求 input 上限。

运行时基于 `27c566954fb1fdd85c766349db51e303ba24dae2` 加本批区域估算修正。评测脚本用局部 patch 准确还原旧切点/区域估算，再单独试一个保留目标；没有新增生产参数或 Loop 分支。

## 决策

历史 usage 与片段大小混用是可由离线等价性测试证明的计量错误，修正应当独立交付。旧策略三次压缩、修正后的 20k 零次压缩，说明切点变化确实影响了真实任务；不过修正后的总成本并非每条都更低，不能宣传为确定的成本收益。

8k 在两次 multi_repo 中实际压缩并继续完成任务。紧邻摘要的 task input 分别为 16,736→10,810、15,238→11,898，摘要各花费 3,245+1,302、3,069+1,311 input+output；重建与最终外部测试通过。相邻请求还新增了工具 observation，因此这只是观察到的请求大小变化，不是保持其他消息不变的净节省量。

8k 相比 content20k 的四条总 input 方向为降低、增加、降低、降低。real_repo 两次都没有压缩，差异无法归因于近期目标；multi_repo 的累计 input 分别低 21.2% 和 7.8%，但请求含摘要分别多 2 次和 1 次。总体请求同为 69，input 低 11.6%，output 高 21.2%，耗时高 10.2%。小样本尚未形成成本和效率的稳定改善证据，因此不把 8k 设为默认；也不降低工具结果占比或回本门槛来强行制造压缩。后续复验应覆盖更多确实触发压缩的长任务和多轮会话。

工具错误按 `is_error` observation 计，bash 普通非零退出不计入；content20k 第二次 multi_repo 有一次工具错误但最终修复通过。验证命令与同参重复读取沿用 M8.0 口径，不能直接视为验证强度或无效工作量。

## 验证与边界

离线测试确认携带不同历史 usage 的相同消息获得相同切点、区域成本与工具占比；携带 120k input usage 的短 assistant 不再遮蔽大工具结果的压缩机会。窗口失败、成本摘要失败、写入失败、未知窗口和恢复沿用既有回归。

聚焦 Context/Session 测试 40 passed，评测回归 12 passed；全量 654 passed / 5 deselected，Ruff、生产包 compileall 与 diff 检查通过。

本批不计算费用、缓存命中或网络分项耗时；未测 OpenAI、其他模型、接近 1M 窗口或长期多任务会话。恢复验证重建后的消息投影、modified_files 和下一请求快照一致，没有在恢复后再发送一次真实请求。任务后外部测试只能检验这两种修复的摘要质量，不能证明所有摘要都完整。
