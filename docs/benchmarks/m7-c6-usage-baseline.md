## C8 的预算决策与后续验证

- **已采用默认关闭、显式 opt-in 的 `--max-run-input-tokens`**：当前没有复杂排障样本，也没有同任务多次对照；任何统一数值都会无依据地截断一部分正常修改任务。
- C8 已用 FakeLLM 覆盖完成回答、复杂工具批次停止、缺失 usage 估算、JSONL 恢复和 CLI 退出语义。B1–B4 尚未调用真实模型，因此不报告成本下降或答案质量改善。
- 后续真实对照在此四类固定场景上记录请求数、Tool 数、累计 Provider input/output、最后请求输入、耗时和质量检查点。至少补齐复杂排障，分别报告各场景结果；不能只展示总 token 下降。
- 再决定是否设默认值：若预算能显著减少只读任务浪费，且修改/排障任务的质量、工具配对和可续跑均通过验收，才将默认值写入 CLI 帮助和 README。否则继续保持 opt-in。
- `context_window - reserve_tokens` 只保护单次请求窗口，不代替累计预算；C8 也不能把 H1 的 157,007 累计 input 当成 1M 窗口的 15.7% 占用。

复核方法：用 `JsonlSession.load(path).active_entries()` 和 `recent_session_run_usage(entries)` 取得最近任务统计；多任务文件对每条用户消息截取活动链前缀后调用同一函数。原始文件仅留在用户目录，不进入仓库。缺失 usage 的请求必须单列覆盖率，不填成零。
