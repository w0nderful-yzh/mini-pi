# M7.6f 旧工具结果提前压缩的成本记录（离线估算）

本记录**不包含真实模型调用**，也不包含任何 Provider 计费数据。全部数字来自仓库内可复现的离线夹具，使用项目统一的字符估算规则（每 4 字符 ≈ 1 token，含工具名、参数与结果正文），口径是**每次请求的输入投影估算之和**——与 H1 的 157,007 累计 input 同类口径，但那是 Provider 实测、这里是估算，两者不可混用。

## 夹具

`tests/session/test_cost_aware_compaction.py` 的固定脚本：两轮任务，每轮一次工具调用。

| 项 | 值 |
| --- | --- |
| 模型窗口 | `deepseek-flash`（1M）；窗口触发在两个分支都不会介入 |
| 第一轮工具输出 | 100,000 字符正文（约 25,000 token） |
| 第二轮工具输出 | 60,000 字符正文（约 15,000 token） |
| 保留预算 | `DEFAULT_KEEP_RECENT_TOKENS = 20,000` |

`before` 分支把成本决策强制为“不压缩”，即 M7.6f 之前窗口内的行为；`after` 分支使用真实决策。除该决策外两个分支的脚本、工具、消息完全一致。

## 记录

| 指标 | before（无提前压缩） | after（成本触发） | 差值 |
| --- | ---: | ---: | ---: |
| 请求数（含摘要调用） | 4 | 5 | +1 |
| 累计输入估算 | 91,062 | 66,960 | **−24,102（−26.5%）** |
| 压缩检查点 | 0 | 1 | +1 |

每次请求的输入估算：

```text
before: [253, 25,264, 25,267, 40,278]                  # 最后一次请求重发全部历史
after:  [253, 25,264, 25,267, 890, 15,286]             # 890 是摘要调用本身
```

摘要调用只花 890 token：两条工具输出在进入摘要请求前按 `TOOL_RESULT_LIMIT`（每条 2000 字符）头部截断并标记省略量，因此**摘要成本与工具输出长度基本无关**，而每次后续请求省下的正是完整输出。这正是“成本感知”成立的前提，也是它需要被单独证明的原因。

## 生效条件

`mini_pi/context/cost.py` 的纯函数判定，全部成立才提前压缩（调用前即可算出，不通过就不调用模型）：

1. 位置在工具轮之间（`prepare_next_turn`），后面还会有请求；
2. 被摘要区域里 `ToolMessage` 占的 token ≥ 50%（否则收益来自普通对话，交给窗口阈值）；
3. 摘要不比区域大（`saved_per_request > 0`）；
4. 按 `ASSUMED_REMAINING_REQUESTS = 3` 次后续请求计算净收益为正；
5. 有安全切点、工具批次配对完整、窗口已知。

摘要体积在首次压缩时按 `ASSUMED_SUMMARY_TOKENS = 2,000` 上界估计（无历史摘要可参考），重复压缩改用上一次摘要的实测规模。摘要失败只放弃这次优化，不改变本次 run 的结果；**窗口触发**（M7.6d）的失败语义不变。

## 边界

- 这些数字**不能**用来声称真实费用下降：没有价格表、没有缓存命中数据、没有 Provider 实测 usage；FakeLLM 不返回 usage，`CompactionEntry.usage` 保持为 `null`。
- 请求数 4 → 5 说明提前压缩本身要多发一次摘要请求；收益来自后续请求的投影变小，`ASSUMED_REMAINING_REQUESTS` 就是对这个“后续”的显式假设，样本 H1（11 次请求/任务）中该假设成立。
- 真实对照仍需在 `docs/benchmarks/m7-c6-usage-baseline.md` 的 B1–B4 上进行；在此之前不报告真实成本改善，也不把小样本比例外推到 1M 窗口占用（H1 的 157,007 累计 input 从来不是 15.7% 窗口占用）。
